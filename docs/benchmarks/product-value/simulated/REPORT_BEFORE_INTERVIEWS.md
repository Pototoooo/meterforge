# MeterForge 产品价值评测报告｜模拟任务研究

**编制日期：2026-09-11｜用途：产品方案评审、作品集方法展示与面试演练**

> 数据声明：本报告按真实任务评测的结构编写。其中接入、运营和理解度数据为人工设定假设后生成的模拟记录，没有真实参与者、访谈或付款。基线与改进版均为情景定义，不代表两版产品已经上线并完成用户测试。第六节单独引用已有自动化实测，不将两种证据混为一谈。

## 一、摘要：把“事件接入”定义成“客户能使用的正确计量”

MeterForge 的价值不应只用事件吞吐解释，还应体现在接入方能否正确配置计量、运营能否解释异常，以及业务人员能否理解使用成本。本报告据此设计三个任务研究，并用一组明确的模拟假设演示如何判断产品改进是否值得投入。

| 核心指标（模拟） | 基线情景 | 改进情景 | 差异 |
|---|---:|---:|---:|
| 接入任务完成率，含获得帮助后完成 | 17/24，70.8% | 22/24，91.7% | +20.8 个百分点 |
| 运营根因定位正确率 | 23/36，63.9% | 31/36，86.1% | +22.2 个百分点 |
| 计费理解答题正确率 | 26/40，65.0% | 35/40，87.5% | +22.5 个百分点 |

这些差异是**情景设定的计算结果，不是实证预测**。它们用于演示产品取舍，不能证明真实效果或因果关系。即便在这组偏改善的假设下，改进情景仍保留两项接入失败、五项定位错误和一次运营关键误操作，因此不建议只凭总体得分宣布可上线。

## 二、问题背景与产品假设

已有自动化验收提供了三个可用的产品线索：事件能成功接收但存在业务验证错误；未绑定客户时聚合量仍可能可见；默认本地接口中的 subject 声明不构成鉴权。这些事实支持“需要验证以下问题”，但不能直接推出用户会犯什么错误、多久能完成或改版会提升多少。

| 研究问题 | 产品假设 | 拟验证的改进 |
|---|---|---|
| 首条事件返回成功后，接入方是否误认为配置完成？ | 缺乏端到端验收会遗漏客户归属与维度错误 | 上手流程包含客户绑定、能力模板、发送样例、查询校验四步 |
| 运营能否区分接收失败与异步验证失败？ | 状态混合和查询分散提高定位成本 | 分开显示“已接收、验证结果、聚合结果”，关联错误事件与客户 |
| 业务人员是否知道谁承担模型成本？ | 把模型技术明细作为入口增加理解负担 | 业务作业消费摘要优先，平台/自备模式清晰，技术细节按需展开 |

前两项属于 MeterForge 产品问题；第三项属于 LoreLattice 的计费体验，不能当作 MeterForge 自身支付能力。

## 三、实验设计与数据口径

### 3.1 任务样本

| 模拟研究 | 合成角色 | 每个角色任务数 | 每个版本记录数 |
|---|---:|---:|---:|
| 接入 | 8 个开发/平台角色 | 3 | 24 |
| 运营 | 6 个运营角色 | 6 | 36 |
| 理解度 | 8 个业务使用角色 | 5 | 40 |

两版共 **200 条模拟任务记录**，不是 200 名用户或独立样本。ID 均以 `SYN-` 开头，每条记录都有 `data_origin=synthetic_assumption`；不附真实姓名、工作经历、访谈引语或录屏编号。

- **基线情景**：接入方依赖通用 API 文档；运营以原始日志和分散查询为主；使用者首先看到技术用量明细。
- **改进情景**：提供能力模板与客户映射检查；运营使用状态分层和事件追溯；使用者首先看到余额与作业消费摘要。
- 接入上限 30 分钟，运营上限 20 分钟。未成功任务按上限记录；所有任务保留在分母。
- 时间指标是“完成或达到上限的任务耗时中位数”，不是仅成功者的完成时间，也不是首条 API 返回时间。
- 完成率允许获得帮助；独立完成率额外要求成功且未获得帮助。理解率的分母为题目，不能写成用户通过率。
- 真实执行时应采用任务难度相当的替代任务和顺序平衡，避免重复做同题的学习效应；本次没有实际分组、招募或 A/B 投放。

### 3.2 模拟值怎么产生

`simulated/generate.py` 显式指定各任务的成功、求助和误操作结果，并按固定公式分配时长。不是从真实行为拟合模型，也没有市场基准或置信区间。改变这些输入假设就会改变差异，不能把计算精确度当作预测准确度。

保留未改善项用于演示失败复盘；但这些具体失败归属仍是设定，不是已发现的真实用户问题。

## 四、分项结果与产品解读

### 4.1 接入：完成任务还不等于能独立接入

| 指标（模拟） | 基线情景 | 改进情景 |
|---|---:|---:|
| 完成任务 | 17/24，70.8% | 22/24，91.7% |
| 独立完成任务 | 9/24，37.5% | 20/24，83.3% |
| 发生求助的任务 | 15/24，62.5% | 4/24，16.7% |
| 达到时限仍未完成 | 7/24 | 2/24 |
| 含超时任务的耗时中位数 | 23.0 分钟 | 13.5 分钟 |

情景中的耗时中位数下降 **41.3%**。其中独立完成与含帮助完成的差距更值得关注：如果真实测试出现类似差距，仅展示“完成率”会掩盖接入仍依赖人工支持。

**建议决策：** 把“首个成功 HTTP 响应”改为“首条客户归属正确、无验证错误并可查询的用量”。拟议接入包应包含 LLM Token、ASR 秒数模板，以及客户映射的自检结果，不只是复制一段请求代码。

### 4.2 运营：先看定位与安全，再看速度

| 指标（模拟） | 基线情景 | 改进情景 |
|---|---:|---:|
| 根因判断正确 | 23/36，63.9% | 31/36，86.1% |
| 获得帮助的任务 | 18/36，50.0% | 6/36，16.7% |
| 含超时任务的耗时中位数 | 15.5 分钟 | 7.0 分钟 |
| 关键误操作 | 3/36，8.3% | 1/36，2.8% |

情景中的耗时中位数下降 **54.8%**，但仍有五项根因错误和一次关键误操作。此处关键误操作定义为导致错误数据处理的操作，例如在未查明归属时重新归属或重放事件；本次没有真正操作任何客户数据。

**建议决策：** 若未来真人测得这种结果，可以继续试用查询与解释功能，但自动补偿、重归属和重放入口应另设验证及确认门槛。不要用定位速度下降来抵消资金或归属操作风险。

### 4.3 理解度：业务解释比技术字段更重要

模拟问卷五题分别验证：谁付模型费、本次成本如何形成、何时余额到账、自备 Key 是否扣平台余额、调用失败如何处理。

- 基线：26/40 题正确，65.0%。
- 改进：35/40 题正确，87.5%。
- 差异：+22.5 个百分点；不是“提升 22.5%”。

**建议决策：** 将收费方式和状态解释置于主页面，模型 Token 与价格版本保留为下钻信息。但正确答题不代表真实付款意愿，不能推算充值转化率、客单价或留存。

该部分只演示 LoreLattice 计费页面的产品验证方法；没有测试支付宝真实支付，也不代表 MeterForge 具备已验证的收款闭环。

## 五、假设敏感性：不要让一个漂亮数字决定开发优先级

下表固定基线，仅改变改进情景中成功任务的假设数量。它是备选设定，不是统计置信区间或发生概率。

| 指标（模拟敏感性） | 无改善设定 | 较小改善设定 | 本报告主情景 |
|---|---:|---:|---:|
| 接入完成任务 / 24 | 17（70.8%） | 19（79.2%） | 22（91.7%） |
| 正确定位任务 / 36 | 23（63.9%） | 27（75.0%） | 31（86.1%） |
| 正确回答 / 40 | 26（65.0%） | 30（75.0%） | 35（87.5%） |

由于没有真人基线，不能确认主情景比另两种更可能出现。优先实施客户映射检查和验证状态区分，是因为已测到相应的接入风险，而不是因为模拟表给出了四成或五成效率改善。

## 六、已有实测支撑与边界

以下仅引用 `REPORT.md`、`SUMMARY.json` 中 2026-09-11 的已归档自动化结果，本轮没有重新启动服务或重复实测：

| 已有实测项 | 已记录结果 |
|---|---|
| 唯一业务事件 | 五类能力、三轮，共 15,000 条 |
| 主集重复重试 | 3,750 次，后续聚合未增加 |
| 维度对账 | 120/120 组与独立预期一致 |
| 消费暂停积压恢复 | 三次共 1,500 条全部补齐 |
| 恢复后再次重试 | 1,500 次，数量未增加 |
| 信封格式无效输入 | 12/12 次同步返回 400 |
| 业务语义无效输入 | 12/12 次先返回 204；缺失/非数字有异步错误，错误单位/负数进入聚合 |

被测为固定本地镜像与合成事件，不是生产业务或当前 main 的完整验收。以上只能证明指定环境的行为；不能用于“推导”模拟角色的成功率和时间。

## 七、行动计划与验收门槛

| 优先级 | 拟议动作 | 后续实际验证 |
|---|---|---|
| P0 | 接入检查包含客户映射、单位和数值策略 | 首条可用事件必须客户归属正确、无验证错误；保留负例 |
| P0 | 说明服务端可信接入与租户凭证边界 | 单独测试凭证/namespace/customer 绑定，不用 subject 过滤替代 |
| P1 | 设计已接收、验证结果、聚合结果的分层反馈 | 用相同难度的故障剧本测试定位正确率与求助情况 |
| P1 | 业务作业消费摘要优先，技术明细下钻 | 测理解题及查找费用任务，不用浏览量替代理解 |
| P2 | 在安全门槛满足后评估运营重放/补偿入口 | 高风险误操作作为独立阻断项，不被平均得分覆盖 |

**建议下一轮真人研究：** 先各找两名开发者和运营人员做试测，检查任务可理解性和时间上限，再开展原计划样本。两人试测只能完善方法，不报告总体转化或显著效果。归属/资金关键错误为零是建议安全门槛，而非本模拟已验证的结果。

## 八、作品集与简历表达

### 可准确使用的模拟研究表述

> 基于 MeterForge 接入与异常计量场景，构建接入完成率、根因定位正确率和计费理解率三类产品指标；设计 200 条模拟任务记录与多情景分析，明确独立完成、求助、超时和误操作的验收口径，并将客户映射检查与异步错误反馈列为优先验证方向。

### 可与已有实测组合的表述

> 为 AI 计量平台设计产品验收体系，在固定本地环境完成 1.5 万条合成事件和 3,750 次重复重试，验证 120 个细分组对账及 1,500 条积压补记；进一步以模拟任务研究设计接入与运营体验指标，区分技术成功、业务有效和用户价值，形成产品改进优先级。

不应删去模拟限定后写成“接入效率提升 41.3%”“运营效率提升 54.8%”“访谈 22 名真实用户”或“付费转化提升”。如果未来完成真人研究，应以实测记录替换模拟表，而不是仅删除数据来源说明。

## 九、交付与复算

- `simulated/SYNTHETIC_TASKS.csv`：200 条模拟任务记录，每行带来源标识。
- `simulated/SIMULATED_SUMMARY.json`：计算结果。
- `simulated/generate.py`：全部显式假设与生成逻辑。
- `simulated/VALIDATION.json`：独立复算与数据检查。
- 原 `REPORT.md`、`SUMMARY.json`、真人招募空表及原始 HTTP 记录保持不变。

复算命令：在本项目根目录运行 `python3 docs/benchmarks/product-value/simulated/generate.py`。这只生成模拟文件，不访问模型、支付或 MeterForge 服务。
