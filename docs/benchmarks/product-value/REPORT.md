# MeterForge 产品价值实验报告

**执行日期：2026-09-11｜类型：本地实服务、合成业务事件、自动化产品验收**

## 结论先行

MeterForge 的基础计量链路在本轮受控测试中可以支撑“用量可信、可重试、可回溯”的产品承诺；但**接收成功不等于业务校验通过，主体归属不等于多租户鉴权**。当前证据适合产品简历中的验收设计、风险识别与优先级判断，不支持用户增长、收入或接入效率改善结论。

- 三轮、五类模型共 **15,000 条唯一事件 + 3,750 次重试**，15 个模型×运行总量及 **120 个细分组**与独立 oracle 一致，最终再次读取未出现额外数量。
- 三次消费服务暂停，共 **1,500 条积压事件全部补齐**；恢复后再重试这 1,500 条，聚合量不增加。解除暂停至查询看到完整积压的时间为 **1.033 / 3.072 / 3.071 秒**。
- 12 个 CloudEvents 信封无效输入全部同步返回 400；另外 12 个业务无效输入全部先返回 204，其中缺失数量、非数字随后可查到异步验证错误，错误单位和负数则参与了聚合。
- 真实参与者 **0**，真实支付 **0**。首次接入耗时、运营定位效率、理解率、转化率仍待真人实验，不能用脚本时长替代。

## 1. 被测对象与归属

本轮使用独立 Compose 项目 `mf-product-value`，HTTP 只绑定 `127.0.0.1:39888`。包括 MeterForge API、sink-worker、Kafka、ClickHouse、Redis 和 PostgreSQL，不启动支付或订阅任务。完成后已拆除本轮容器与网络；不停止或修改原 quickstart 或 LoreLattice 服务。

被测应用镜像：`sha256:06052c76009f63d136f8ae6366451e5f1a21f1466a25afbdbb6706769cbfe8dc`。镜像记录的创建时间是 2026-07-28；没有证明它由当前 checkout 构建，因此报告**不是当前 main 源码的完整验收**。镜像/源码快照分别见 `raw/image.json`、`raw/source.txt`。

事件形状模拟 LoreLattice 五类能力，但本轮**没有通过 LoreLattice 的真实模型调用链生成事件**，没有调用收费模型。BYOK 成本为 0、平台价格版本与金额字段由测试夹具提供；MeterForge 只验证这些维度和数值的聚合，不证明其价格引擎或真实钱包结算。

## 2. 方法与分母

三轮正式运行以 `mapped_customer_v2` 标记，每轮先创建两名合成客户并绑定 subject，使用新的事件类型、计量器和 ID，防止污染上轮结果。固定随机种子 20260911，打乱输入顺序。

每轮内容：

1. LLM / Embedding / Rerank / VLM / ASR 各 1,000 条唯一事件。每条数量为 1–17；每类数量总和为 8,979。前四类单位是 Token，ASR 是秒，**不把异单位加成业务总用量**。
2. 20% 的主事件时间戳约早两天，乱序批量提交；每类重试原始 250 条。以 `(source,id)` 独立去重重算预期值。
3. 每类查询 subject、model、billing_mode、price_version 的八个实际组合，每轮 40 组；三轮合计 120 组。
4. 每类抽查一个确定事件的原始数据、客户 ID 和 validationError，共 15 条；这是样本可追溯性，不是全部事件追溯率。
5. 每轮已有 100 条基线事件后暂停 sink-worker；提交 500 条，至少保持五秒后验证可见量仍为 100；解除暂停，验证 600 条，再重试 500 条。
6. 每轮在 200 条基线已查询后补发 200 条七天前事件；期望值从 400 增至 1,000。三轮共 600 条晚到事件。
7. 独立空计量器作为零值对照；无效事件使用独立计量器，避免负值影响正常结果。

主集 15,000 条不含恢复/晚到场景、语义负例、主体声明探针和诊断试测。主集重试 3,750 次与恢复后重试 1,500 次分别列出。HTTP 以最多 100 条/批发送，HTTP 请求数不等于事件数。

没有参与者 A/B 实验，没有声称 SDK 优于裸 API，没有统计显著性或总体可靠性估计。

## 3. 产品验收结果

| 产品问题 | 结果与分母 | 能说明什么 |
|---|---|---|
| 五类能力是否可统一表达并准确聚合？ | 15/15 模型×运行总量一致；主集 15,000 条 | 本夹具范围内支持多能力用量归集 |
| 重试是否增加用量？ | 15/15 总量在 3,750 次原始重试后不变，后续最终读取仍一致 | 支持该观察窗口内的幂等重试，不是无限期 exactly-once 承诺 |
| 客户/模式/版本能否细分？ | 120/120 组合一致；30/30 单客户过滤查询一致 | 可做细分用量分析；不等于客户凭证隔离 |
| 生产者提供的成本字段能否正确汇总？ | 15/15 成本聚合一致，BYOK 输入成本为零 | 仅验证成本元数据聚合，不是账单或扣款验证 |
| 异常消费能否恢复？ | 3/3 次补齐，每次 500 条；重放后仍 600 条 | 三次受控暂停恢复的结果完整性 |
| 七天前的晚到事件能否补记？ | 3/3 次一致，共 600 条晚到事件 | 本地默认配置支持这些晚到事实 |
| 查询能否追溯业务来源？ | 15/15 抽样事件保留客户、作业、模型、单位、模式、版本 | 样本可解释性成立，不证明运营人员能高效使用 |
| 用量多久可见？ | 15 批场景：最后一批发送后可见时间中位数 1.029 秒，范围 1.021–1.050 秒 | 1 秒轮询粒度的整批可见性，不是逐事件延迟或生产 P95 |

恢复到可见时间是**解除暂停后查询完整结果**的时间，不能写成“告警到修复只需 1 秒”或人工 MTTR。

## 4. 失败与边界比成功率更有产品价值

### 4.1 接收成功与业务有效要分开显示

缺失 ID、缺失 source、错误 specversion、错误时间各三次，共 12 次均返回 HTTP 400。

另四种业务语义探针各三次均先返回 204：

| 输入 | 查询到的处理结果 | 产品含义 |
|---|---|---|
| 数量 10，单位 `banana` | 无验证错误，计入 10 | 通用数值计量器不自动理解业务单位；需接入端 schema/单位校验 |
| 数量 -2 | 无验证错误，计入 -2 | 对本场景是无效消费，但通用计量器可能允许冲正；业务策略必须显式配置 |
| 缺失 quantity | 原始事件显示缺失 value property | 已接收后异步无效，不能把 204 当“成功计费” |
| quantity 为 `ten` | 原始事件显示不能解析浮点数 | 需要无效事件查询和清晰的状态反馈 |

每轮语义计量器实际结果均为 **8（10 - 2）**。这不是“12 个坏事件全部静默扣费”：缺失和非数字两类有异步错误记录。

**产品决策建议：** 明确“已接收 / 已验证 / 已聚合”三个状态；提供按模型能力的单位与非负值接入模板，以及无效事件入口。是否在 MeterForge 通用层拒绝负数应由业务策略决定，不应直接一刀切。

### 4.2 subject 是声明，不是权限

三次向默认未鉴权的本地接口声明 `other_workspace`，均被接收，聚合值均为 999。原始客户映射与 subject 过滤不能构成外部调用方的授权检查。

**产品决策建议：** 将可信服务端接入的部署边界写入上手文档；如要开放多租户写入，需独立测试凭证与 namespace/customer 的绑定，当前结果不能称为“租户越权漏洞已验证”，更不能称为“跨租户隔离率 100%”。

### 4.3 客户映射是接入成功定义的一部分

正式三轮之前有一次未绑定客户的诊断试测：总量正确，原始事件却显示 `no customer found for event subject`。这直接说明“首条事件返回 204”不足以定义产品激活。

**修订激活指标：** 首条被接收、客户归属正确、没有验证错误且可在预期维度查询的事件。诊断试测全部保留在 `raw/20260911_030759_d21e6b/`，不混入正式成功率。

## 5. 哪些仍未测试

## 6. 可用于简历的表述

> 面向 AI SaaS 用量可信与故障恢复，设计 MeterForge 产品验收矩阵；在固定本地镜像上完成三轮、五类能力共 1.5 万条合成事件与 3,750 次重复重试，验证 120 个客户/模型/计费模式/价格版本组合与独立预期一致，并在三次消费暂停场景下完成 1,500 条积压补记。

> 通过事件追溯与业务负例发现“接收成功≠有效计量”的接入风险，区分同步格式校验、异步业务验证与租户授权边界，提出客户归属校验、单位约束模板及无效事件反馈的产品优先级。

这些描述是**受控产品验收**，不能改写成生产客户规模、用户转化提升、避免了多少真实损失、总体 99.99% 准确率或真实收入。

## 7. 证据和复现

- `PLAN.md`：原始方案及本轮范围修订。
- `SUMMARY.json` / `METRICS.csv`：三轮汇总与逐模型明细。
- `raw/<run>/http.jsonl`：实际请求体、响应体、HTTP 状态、请求耗时、时间戳。
- `raw/<run>/*-oracle.json`：初始独立预期；`analyze.py` 再从实际提交事件重新去重计算，检查数量、成本和分母。
- `raw/<run>/runner.py`：执行脚本快照。
- `FINAL_READBACK.json`：三轮执行后对 15 个主计量器再次查询的原始结果。
- `raw/<run>/pause.json` / `unpause.json`：实际故障注入命令、返回码及输出。
- `raw/initial-errors.txt`：前期夹具编写与配置错误。编译失败草稿不是性能或产品证据。
- `VERIFICATION.txt` / `SHA256SUMS.txt`：验证与文件完整性记录。

在 MeterForge 根目录：

```sh
make -C docs/benchmarks/product-value up
make -C docs/benchmarks/product-value test  # 每次产生独立 run，正式实验需三轮
python3 docs/benchmarks/product-value/analyze.py
make -C docs/benchmarks/product-value down
# 已归档结果可离线复算，不依赖运行中的服务：
python3 docs/benchmarks/product-value/analyze.py --offline
```

脚本退出 0 表示流程执行完毕，不代表所有产品探针通过；各项 `passed` 值和失败响应均保留。已归档三轮后再次复现实验，应在新实验目录运行，避免超过 `analyze.py` 对“恰好三轮”的明确检查。Compose 使用本机固定镜像 ID，另一台机器须先获取同一镜像；依赖测试账号不是生产凭证。
