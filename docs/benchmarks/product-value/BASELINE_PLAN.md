# MeterForge 产品价值实验方案

> 目标：为产品简历提供 MeterForge 的产品能力证据。本文中的目标值是实验设计目标，不是已完成结果。

## 当前证据边界

此前 MeterForge 实验主要验证共享幂等写入的技术选型：Redis 与 PostgreSQL 均通过双实例重复事件验证，Redis 在 15 组对照中吞吐中位数高 22.76%，P95/P99 延迟分别低 14.22%/50.05%，哈希键使 Redis 事件内存下降 20.09%。这些结果能说明工程判断，但不能直接说明计量产品更易接入、更可信或更有商业价值。详见 `meterforge/docs/meterforge-testing-and-technology-selection.md` 和 LoreLattice 既有 benchmark 报告。

本轮产品实验应把 MeterForge 当作“用量计量与计费基础设施”，把 LoreLattice 当作真实接入方。余额与支付宝支付由 LoreLattice 本地账本负责；MeterForge 只接收新钱包事件 `lorelattice.wallet.usage.v1`，因此不能把 LoreLattice 的充值金额、收入或支付转化率写成 MeterForge 的支付指标。

## 实验一：接入效率

**问题**：一个新的 AI 产品团队能否快速完成 MeterForge 接入，并正确表达不同模型的计量规则？

**设计**：准备 3 个接入任务：LLM Token、ASR 秒数、BYOK/平台模型混合归属。由 5–8 名具备后端经验但不了解项目内部实现的参与者，分别使用“裸 API 文档”和“SDK + 示例配置”完成任务。每人只做一次，记录屏幕、操作日志和最终配置。

**核心指标**：

- 首次成功时间：从打开文档到第一条有效用量事件被 MeterForge 接收的分钟数。
- 配置一次成功率：首次提交即通过 schema、事件字段和计量结果校验的比例。
- 有效事件时间：从服务启动到第一条可查询、维度正确的事件的分钟数。
- 计量规则错误率：单位、聚合、字段路径、客户归属等错误任务数 / 总任务数。
- 文档求助率：需要查看非预期文档、源码或人工帮助的参与者比例。

**建议目标**：SDK + 示例配置相对裸 API 文档，首次成功时间下降 40%，配置一次成功率达到 80% 以上，计量规则错误率低于 10%。目标是待实验验证的门槛，不应提前写成结果。

**简历表达模板**：

> 以 LLM、ASR 和 BYOK 混合计量为任务，设计 MeterForge 接入可用性实验，比较裸 API 与 SDK/示例配置路径，跟踪首次成功时间、一次配置成功率和计量规则错误率，定位接入流程中最影响激活的步骤。

## 实验二：计量可信度

**问题**：产品团队能否相信 MeterForge 记录的用量，并解释每笔费用从哪里来？

**设计**：构造固定事件回放集：唯一事件、重复事件、乱序事件、延迟事件、缺少可选字段事件、错误单位事件、跨租户事件。每类至少 1,000 条；同时保留 LoreLattice 本地账本作为独立对照。事件采用唯一 `event_id`，结果按客户、能力、模型、时间窗口和业务作业聚合。

**核心指标**：

- 计量准确率：MeterForge 聚合值与独立 oracle 的绝对误差不超过 1e-6 的事件/窗口比例。
- 重复事件抑制率：重复事件未造成额外计量的比例。
- 跨租户隔离率：错误归属被拒绝或隔离的比例。
- 账本对账差异率：`abs(remote - oracle) / max(oracle, 1)`。
- 解释完整率：每条费用是否能回溯到 workspace、业务作业、模型、单位、单价版本和原始事件。
- 处理延迟：事件产生到可查询聚合结果的 P50/P95。

**建议目标**：重复事件抑制率和跨租户隔离率达到 100%；有效事件计量准确率达到 99.99%；对账差异率低于 0.01%；95% 的用量在 60 秒内可查询。若未达标，应保留原始事件和差异样本，不用平均值掩盖问题。

**简历表达模板**：

> 为 AI 用量计量建立独立 oracle 和异常事件回放集，覆盖重复、乱序、延迟、跨租户和错误单位场景；以计量准确率、重复抑制率、账本差异率和可解释性作为验收指标，形成从原始事件到费用结果的可追溯验证链。

## 实验三：运营排障效率

**问题**：运营或财务人员能否在不读代码的情况下定位计量异常？

**设计**：准备 6 个故障剧本：重复计量、事件延迟、客户归属错误、单位配置错误、价格版本不一致、下游暂时不可用。让 5 名产品/运营/财务角色使用 MeterForge 控制台、事件查询和 LoreLattice 用量页处理问题。每个剧本使用不同参与者，避免记忆效应。

**核心指标**：

- 首次定位时间：打开监控到指出根因的分钟数。
- 正确定位率：根因、影响范围和受影响客户均判断正确的比例。
- 修复闭环时间：从发现到补偿、重放、隔离或升级处理完成的分钟数。
- 证据完整率：处理记录是否包含事件 ID、客户、时间窗口、影响量和处置动作。
- 误操作率：错误重放、重复退款、错误客户修复等次数。

**建议目标**：正确定位率达到 80% 以上，P95 首次定位时间低于 15 分钟，误操作率为 0，证据完整率达到 95%。

**简历表达模板**：

> 以计量重复、延迟、归属和价格版本异常设计运营排障任务，测量定位时间、根因判断准确率、修复闭环时间和误操作率，把 MeterForge 的事件可观测性转化为可衡量的运营效率收益。

## 实验四：产品激活与付费体验

**问题**：用量信息是否帮助 LoreLattice 用户完成首次有效使用，并减少对扣费的疑虑？

**设计**：在 LoreLattice 中做两版界面：A 版显示余额、一次业务作业消费和充值状态；B 版显示原有按能力/Token 的技术明细。使用任务随机分流，任务为“配置平台模型、完成一次问答、查看消费、创建充值订单并确认状态”。真实支付未启用前，只测订单创建、待付款、已付款 webhook 模拟和余额到账；不得把模拟充值写成真实收入。

**核心指标**：

- 首次价值时间：从进入工作空间到完成第一条有效回答的分钟数。
- 计费理解正确率：用户能否正确回答“本次扣了多少、为什么扣、余额何时到账”。
- 充值漏斗：充值入口点击 → 订单创建 → 支付页面打开 → 支付确认 → 余额到账。
- 订单异常率：重复点击、重复通知、金额不一致、跨 workspace 访问等安全负例的拦截率。
- 用量页任务完成率：查看消费并定位一笔费用的成功比例。
- BYOK 误解率：用户是否错误认为自备 Key 会扣平台余额。

**建议目标**：计费理解正确率达到 85% 以上，订单安全负例拦截率 100%，充值到账状态与后端订单状态一致率 100%。在正式支付开通前，只能报告模拟 webhook 和测试订单结果。

**简历表达模板**：

> 将复杂的套餐/Token 体系收敛为 Workspace 共享余额，设计余额、用量和支付状态的用户任务实验；用首次价值时间、计费理解正确率、充值漏斗和异常订单拦截率验证收费体验，而不是只展示接口已接通。

## 实验数据模型

每条实验记录至少包含：

```json
{
  "experiment_id": "mf-product-2026-09-01",
  "participant_id": "p01",
  "task_id": "onboarding-llm",
  "variant": "sdk_example",
  "started_at": "2026-09-11T00:00:00Z",
  "completed_at": "2026-09-11T00:12:31Z",
  "success": true,
  "help_requested": false,
  "first_valid_event_id": "evt_123",
  "metered_quantity": 1200,
  "oracle_quantity": 1200,
  "reconciliation_error": 0,
  "root_cause": null,
  "evidence_complete": true
}
```

不要记录 API Key、支付私钥、完整买家信息或可识别的个人数据。每个参与者使用合成 workspace、合成模型和合成事件。

## 推荐的首轮样本量与分析

首轮可用 6 名参与者、4 个任务族、每个任务 2 个界面/接入变体；这适合发现问题和形成产品故事，不足以证明统计显著的总体提升。事件回放和对账实验可以扩大到 10,000–100,000 条合成事件，报告准确率、异常拦截率和延迟分位数。

报告同时给出绝对值和分母，例如“7/8 次首次配置成功”，不要只写“成功率提升”。任务实验记录中位数和 P95；事件实验记录准确率、重复抑制率、跨租户隔离率和对账误差；运营实验保留每个故障剧本的原始操作日志。

## 最适合简历的最终组合

优先完成三项：

1. **接入效率**：证明 MeterForge 让新计量能力更快接入。
2. **计量可信度**：证明复杂异常事件下结果仍可对账、可解释。
3. **运营排障效率**：证明事件和用量视图能减少定位与修复时间。

支付体验作为 LoreLattice 商业化案例单独描述。不要把 LoreLattice 的支付宝充值、余额或收入写成 MeterForge 的产品指标；可以描述为“基于 MeterForge 用量事件设计并落地按量计费接入”。

## 简历 bullet 草稿

> 面向 AI SaaS 的用量计量场景，设计 MeterForge 产品价值评测框架，覆盖接入效率、计量可信度和运营排障效率；以首次有效事件时间、计量准确率、重复事件抑制率、账本对账差异率和根因定位时间建立可复现验收标准。

> 将 LoreLattice 接入 MeterForge 的用量事件模型，统一 LLM、Embedding、Rerank、VLM 与 ASR 的计量维度，并保留 workspace、业务作业、模型、单位和价格版本的可追溯链路；通过异常事件回放验证跨租户隔离、重复抑制和对账一致性。

> 将原有套餐/Token 配额体验收敛为 Workspace 共享余额与按量计费，围绕首次价值时间、计费理解正确率、充值状态一致性和 BYOK 误解率设计产品实验；支付结果仅在正式 webhook 验签后入账。

## 已有证据与本轮缺口

已有：共享幂等写入技术对照、LoreLattice RAG/Agent 质量评测、用户研究中的额度与成本痛点记录。

缺口：接入任务原始操作日志、异常事件回放结果、运营排障任务结果、真实或明确标注的支付漏斗数据。没有这些原始数据时，以上内容只能作为实验方案，不能写成已取得的产品效果。
